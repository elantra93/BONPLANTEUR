## Résumé exécutif

Le thème visuel a bien été refait aux couleurs agricoles et plusieurs services transverses (RBAC, offline, validation, image) ont été créés et sont réellement branchés dans une partie de l'UI — sur ce point les audits de juin sont dépassés. Mais l'état réel du projet est plus grave que ce que les constats préliminaires laissaient supposer :

- **Les règles Firestore déployées dans le repo sont ouvertes en lecture/écriture publique (`if true`) sur la quasi-totalité des collections métier**, y compris la collection `revenus` qui autorise `write` et `delete` sans aucune authentification. C'est la faille la plus critique du projet (P0-1).
- **Le flux d'authentification réellement atteignable par l'utilisateur n'est pas celui décrit dans CLAUDE.md.** L'app démarre sur un écran email + mot de passe libre (`CreateAccount1Widget`), sans lien vers le flux téléphone/OTP (`LoginPhonePageWidget`/`OTPVerificationPageWidget`) qui existe dans le routeur mais n'est appelé nulle part dans l'UI. La règle 🔒 « phoneToEmail » n'est implémentée dans aucun chemin de code actif (P0-2).
- **Un utilisateur qui s'auto-inscrit obtient un compte sans aucun rôle** (`roles: []`), et rien dans le routage ou l'UI ne bloque l'accès au tableau de bord dans ce cas (P0-3).
- Le module **Campagnes** et tout le **moteur financier** (`revenu_attendu`, `taux_consommation_budget`, ventilation des frais généraux) décrits comme colonne vertébrale de CLAUDE.md §4/§5 **n'existent pas du tout** dans le code — pas seulement « non testés ».
- Le **tableau de bord** actuel est encore la version FlutterFlow d'origine (cartes « Mes exploitations / Mes parcelles / Activités à venir / Stocks »), pas la maquette à 4 tuiles 2×2 + jauge budget + 5 dernières activités décrite en §3.1.
- `RequirePermission` existe mais n'est importé nulle part : le RBAC est appliqué ponctuellement (3 endroits) via `RbacService` directement, jamais via le widget prévu pour ça, et les combinaisons de rôles interdites (`hasRoleConflict`) ne sont jamais vérifiées à la création/modification d'un utilisateur.
- La stack technique figée par CLAUDE.md (Riverpod, freezed, json_serializable, Drift, Cloud Functions client) est **absente de `pubspec.yaml`** : le projet tourne toujours sur `provider` + les modèles FlutterFlow bruts, c'est-à-dire que la reconstruction "from-scratch" n'a pas eu lieu au niveau architecture.

Priorisation : **3 P0** (sécurité/bloquant), **6 P1** (majeurs), **5 P2** (amélioration).

## 1. P0 — Critique / Sécurité

### P0-1. Règles Firestore quasi entièrement ouvertes (`if true`)

**Fichier :** `firebase/firestore.rules`

Sur 15 collections, seule `USERS` restreint correctement l'accès (`request.auth.uid == document`). Toutes les autres suivent ce patron :

```
match /exploitations/{document} {
  allow create: if true;
  allow read: if true;
  allow write: if false;
  allow delete: if false;
}
```

→ N'importe qui (authentifié ou non, puisque `if true` ne vérifie même pas `request.auth != null`) peut **lire** et **créer** des documents dans `exploitations`, `activites`, `stocks`, `consommation_stock`, `depenses`, `recoltes`, `notifications`, `collaborateurs`, `Speculation`, `Parcelles`, `Indicateurs`, `Materiels`, `membres_exploitation`, `invitations`.

Pire : `revenus` (lignes ~99-104) autorise **`create`, `read`, `write` ET `delete` à `if true`** — lecture, modification et suppression totalement libres des données de chiffre d'affaires de tous les clients.

Cela viole directement la règle 🔒 n°3 de CLAUDE.md (« create, read, update explicites — jamais write ») de deux façons : `write` est utilisé explicitement (au lieu d'`update`), et surtout aucune de ces règles ne vérifie `request.auth` ni `resource.data.exploitation_ref` — il n'y a **aucun cloisonnement multi-tenant côté serveur**. Le filtrage par `exploitation_ref` (règle 🔒 n°2) n'existe que côté client (dans les requêtes Dart), ce qui n'a aucune valeur de sécurité si les règles autorisent tout.

**Correctif recommandé :**
- Remplacer chaque `allow read/create: if true` par une vérification `request.auth != null` au minimum, puis par un contrôle basé sur les rôles (`get(/databases/$(database)/documents/USERS/$(request.auth.uid)).data.roles`) et sur `exploitation_ref` (comparer avec les exploitations/membres de l'utilisateur).
- Supprimer `write`/`delete` explicites, les remplacer par `update` scoped, avec soft-delete uniquement (cohérent avec règle 🔒 n°4).
- Vérifier en urgence si ce fichier reflète les règles réellement déployées sur le projet Firebase de production (partagé, cf. CLAUDE.md §1) — si oui, il faut redéployer des règles corrigées immédiatement, l'app étant en usage réel.

### P0-2. Le flux d'authentification atteignable par l'UI n'est pas le flux téléphone/OTP prévu par CLAUDE.md

**Fichiers :** `lib/flutter_flow/nav/nav.dart:76-90` (route initiale), `lib/authentification/create_account1/create_account1_widget.dart`, `lib/authentification/login1/login1_widget.dart`, `lib/auth/firebase_auth/email_auth.dart`, `lib/authentification/login_phone_page/*`, `lib/authentification/o_t_p_verification_page/*`.

La route racine (`initialLocation: '/'`, `nav.dart:82` et `89`) et l'`errorBuilder` (`nav.dart:81-82`) redirigent un utilisateur non connecté vers `CreateAccount1Widget()` — un écran **email + mot de passe classique** (`create_account1_widget.dart:187-193` champ « Email », `:293-297` champ mot de passe), qui appelle `emailCreateAccountFunc` (`email_auth.dart:10-16`) → `FirebaseAuth.instance.createUserWithEmailAndPassword`. Aucune conversion `225<10 chiffres>@demeter-app.com` n'intervient dans ce chemin.

Le flux `LoginPhonePageWidget` → `OTPVerificationPageWidget` (censé être *le* mécanisme d'auth, §6 module 1 de CLAUDE.md) est bien déclaré dans `nav.dart:91-107`, mais **aucun bouton, aucun `pushNamed`/`goNamed` dans tout `lib/` ne pointe vers `LoginPhonePageWidget.routeName`** (vérifié par recherche exhaustive) — seul `nav.dart` le référence. C'est une route orpheline, accessible uniquement en tapant l'URL directement.

À l'inverse, `Login1Widget` et `CreateAccount1Widget` (les écrans email/mdp) sont bien reliés entre eux (`create_account1_widget.dart:625` → `Login1Widget`, `login1_widget.dart:424/483/568` → Dashboard/CreateAccount1/MotDePasseOublié) et sont donc le **véritable** parcours utilisateur.

**Conséquence :** la règle 🔒 n°5 (phoneToEmail) n'est simplement pas implémentée dans le code atteignable. Le module d'auth n'a pas été reconstruit conformément à CLAUDE.md ; c'est le squelette FlutterFlow email/mdp d'origine qui sert de porte d'entrée réelle.

**Correctif recommandé :** décision produit à trancher explicitement — soit brancher réellement `LoginPhonePageWidget` comme point d'entrée unique et retirer/masquer `Login1Widget`/`CreateAccount1Widget`, soit mettre CLAUDE.md à jour si le choix produit a changé. Dans tous les cas, ne pas laisser deux mécanismes d'auth concurrents non documentés.

### P0-3. Auto-inscription libre, sans rôle, sans validation de rattachement

**Fichiers :** `lib/backend/backend.dart:776-799` (`maybeCreateUser`), `lib/backend/schema/users_record.dart:121-150` (`createUsersRecordData`), `lib/auth/firebase_auth/firebase_auth_manager.dart:307`.

`maybeCreateUser` est appelé après **toute** connexion/inscription réussie (email/mdp, Google, Apple, téléphone…) et crée un document `USERS/{uid}` s'il n'existe pas, en ne renseignant que `email`, `displayName`, `photoUrl`, `uid`, `phoneNumber`, `createdTime` — **jamais `roles` ni `superieur_id`**. `RbacService.currentRoles` (`rbac_service.dart:14-24`) renverra donc `[]`, et `currentPermissions` sera un ensemble vide.

Combiné à P0-2 (inscription libre via email/mdp, sans invitation ni validation d'un entrepreneur) et au fait que `nav.dart:558` ne vérifie que `requireAuth && !loggedIn` — **jamais le rôle** — n'importe qui peut créer un compte et atterrir sur `DashboardPageWidget` (`create_account1_widget.dart:566-568`) sans qu'aucun garde-fou ne l'empêche d'accéder aux écrans qui ne dépendent pas explicitement de `RbacService`/`RequirePermission` (la majorité, cf. P1-2).

**Correctif recommandé :** supprimer l'auto-inscription libre (le modèle métier de CLAUDE.md est un rattachement hiérarchique via invitation, `superieur_id`), ou au minimum rediriger tout utilisateur sans rôle vers un écran d'attente/erreur au niveau du `redirect` global du routeur, et ne jamais lui donner accès aux données d'une exploitation.

## 2. P1 — Majeur

### P1-1. Module Campagnes et moteur financier : absents, pas seulement non testés

**Recherché et non trouvé dans `lib/` :** aucune occurrence de `campagne` (toutes casses), aucune collection `campagnes` dans `firestore.rules` ni dans le code, et aucune occurrence de `revenu_attendu`, `rendement_attendu`, `prix_vente_cible`, `taux_consommation`, `part_parcelle`, ou de toute logique de ventilation des frais généraux au prorata de superficie.

Le constat préliminaire #6 (« le module Campagnes n'existe pas ») est confirmé, mais il faut le préciser : ce n'est pas seulement un écran manquant, c'est **toute la colonne vertébrale économique de CLAUDE.md §4-§5** qui n'a aucune trace de code — ni modèle, ni calcul, ni test. Le constat préliminaire #7 (« la logique financière n'est pas testée ») est donc en-deçà de la réalité : il n'y a rien à tester, elle n'est pas écrite.

Par ailleurs, les `Parcelles` actuelles portent encore les champs culture/rendement hérités (non vérifié champ par champ ici faute de temps, mais `custom_functions.dart:27` référence encore une collection `parcelles` en minuscule pour une fonction utilitaire — cf. P1-6) ; la dépréciation prévue par CLAUDE.md §4 (« culture canonique sur la Campagne ») n'a pas de sens tant que `Campagne` n'existe pas.

**Correctif recommandé :** traiter Campagnes comme un chantier de fond à part entière (nouvelle collection + écrans de lancement + calculs `revenu_attendu`/`budget` + ventilation), avant de considérer le module Trésor ou Dashboard comme fonctionnels au sens de CLAUDE.md.

### P1-2. `RequirePermission` codé mais jamais branché — RBAC UI très partiel

**Fichier :** `lib/widgets/require_permission.dart` (défini), recherche exhaustive : **aucun `import '.../require_permission.dart'` ailleurs dans `lib/`.**

Le constat préliminaire #4 est confirmé tel quel. En creusant : `RbacService` (qui, lui, fonctionne) n'est appelé directement que dans 3 fichiers UI :
- `lib/champs/activites/detail_activite_page/detail_activite_page_widget.dart:862,1030` (`canPerform`, `canValidateActivite`)
- `lib/tresor/depenses/bottom_sheet_depense_rapid/bottom_sheet_depense_rapid_widget.dart:1007` (`canValidateDepense`)
- `lib/tresor/depenses/details_depense/details_depense_widget.dart:1405` (`canValidateDepense`)

Cela couvre uniquement la validation d'activité et de dépense. Tout le reste de l'UI (création d'exploitation, gestion RH/collaborateurs, gestion du matériel, accès au module Trésor par persona — cf. CLAUDE.md §3.1 « Trésor rôle-gated ») **n'a aucune vérification de rôle dans le widget-tree** ; l'accès dépend uniquement de la navigation (boutons visibles ou non), pas d'un contrôle défensif. Un ouvrier qui atteint une URL de gestion RH par navigation directe ou état incohérent n'est bloqué par rien côté client, et rien côté serveur non plus (P0-1).

**Correctif recommandé :** utiliser `RequirePermission` (ou au moins `RbacService`) systématiquement sur : écrans de gestion RH (`lib/personnel/**`), CRUD Matériel, CRUD Exploitation/Parcelle, et sur les 4 tuiles du dashboard par persona (budget masqué pour l'ouvrier, revenus masqués pour le chef d'équipe).

### P1-3. Combinaisons de rôles interdites définies mais jamais vérifiées

**Fichiers :** `lib/models/role.dart:88-96` (`incompatibleRoles`, `hasRoleConflict`), `lib/services/rbac_service.dart:53` (`validateRoleCombination`).

La logique existe et va même au-delà de CLAUDE.md (bloque aussi `ouvrier`+`chefExploitation`, `lecteur`+`comptable`, `lecteur`+`admin`, en plus de `ouvrier`+`admin` mentionné en exemple). Mais recherche exhaustive : **`validateRoleCombination`/`hasRoleConflict` ne sont appelés nulle part** en dehors de leur propre définition — donc à aucun moment lors de la création/modification des rôles d'un utilisateur (écrans RH/invitations) cette validation n'est invoquée. Rien n'empêche aujourd'hui d'assigner `OUVRIER`+`ADMIN` à un même compte via Firestore ou un futur écran d'admin qui oublierait l'appel.

**Correctif recommandé :** appeler `validateRoleCombination` dans le formulaire d'attribution de rôle (`lib/personnel/**`) et idéalement dupliquer la contrainte côté règles Firestore (validation sur `USERS.roles` à l'écriture) puisque, comme en P0-1, aucune règle serveur ne protège ce champ aujourd'hui.

### P1-4. Dashboard non conforme à la maquette CLAUDE.md §3.1

**Fichier :** `lib/home/dashboard_page/dashboard_page_widget.dart` (921 lignes), doc-comment lignes 17-33.

Le commentaire d'en-tête du fichier lui-même décrit encore l'ancienne spec FlutterFlow : « Cards: Mes exploitations / Mes parcelles / Activités à venir / Stocks ». Recherche des libellés attendus par CLAUDE.md §3.1 (« Consommation du budget », « Planning », « Alertes », « Suivi des stocks », jauge %, liste des 5 dernières activités) : **aucune occurrence**. Un seul `GridView` est présent (ligne 200) mais rien n'indique une grille 2×2 de tuiles-indicateurs avec jauge budgétaire (aucun `percent_indicator`/`CircularPercentIndicator` utilisé dans ce fichier, alors que le package `percent_indicator` est bien présent dans `pubspec.yaml`).

Le sélecteur d'exploitation existe bien comme composant séparé (`lib/components/selecteur_exploitation_widget.dart`, importé ligne 3), c'est un point conforme.

**Correctif recommandé :** réécrire `DashboardPageWidget` selon la structure exacte de CLAUDE.md §3.1 (sélecteur → 4 tuiles 2×2 → liste 5 activités → nav 3 onglets), avec déclinaison par persona (masquer la tuile budget pour l'ouvrier, masquer les revenus du Trésor pour le chef d'équipe). Ce chantier dépend de P1-1 (Campagnes) pour le calcul réel de `taux_consommation_budget`.

### P1-5. Stack technique figée par CLAUDE.md absente de `pubspec.yaml`

**Fichier :** `pubspec.yaml`.

CLAUDE.md §« Stack (figée) » impose Riverpod, freezed + json_serializable, Drift (offline), Cloud Functions (admin privilégié), flutter_image_compress. Aucun de ces paquets n'apparaît dans `pubspec.yaml` (`riverpod|freezed|json_serializable|json_annotation|drift|flutter_image_compress|cloud_functions|build_runner` : 0 occurrence). Le projet utilise toujours `provider: 6.1.5` (state management FlutterFlow d'origine) et les modèles Firestore bruts (`*_record.dart`, pas de `freezed`), et l'offline (`lib/services/offline_service.dart`) ne s'appuie pas sur Drift (à vérifier dans son implémentation, mais aucune dépendance `drift`/`sqlite3` correspondante n'est déclarée en dehors de `sqflite` hérité de FlutterFlow).

**Nuance importante :** ce n'est pas nécessairement un défaut du code existant (le code marche avec `provider`), mais c'est un écart de gouvernance : soit CLAUDE.md documente une cible qui n'a jamais été engagée, soit la migration d'architecture reste entièrement à faire. Dans l'état actuel, qualifier le projet de « reconstruction from-scratch » (CLAUDE.md §1) est trompeur : il s'agit toujours, structurellement, du squelette FlutterFlow d'origine, enrichi de quelques services (RBAC/offline/validators/images) greffés par-dessus.

**Correctif recommandé :** trancher explicitement avec le porteur produit — soit acter que la stack cible a changé (mettre CLAUDE.md à jour), soit planifier la migration réelle (Riverpod, freezed, Drift) avant d'ajouter davantage de fonctionnalités sur l'architecture `provider`/FlutterFlow, pour éviter d'alourdir une dette qui devra être reprise.

### P1-6. Incohérence de casse sur le nom de collection `Parcelles`

**Fichier :** `lib/flutter_flow/custom_functions.dart:27`.

CLAUDE.md règle 🔒 n°1 exige des noms de collection centralisés, casse héritée conservée (`Parcelles`, `Materiels`). Aucun fichier `lib/core/constants/firestore_collections.dart` n'existe (recherché, absent) — **la règle n°1 elle-même n'est pas respectée** : les 21 occurrences de `.collection('...')` trouvées dans `lib/` sont des littéraux dispersés dans `custom_functions.dart`, les fichiers `*_record.dart` de `lib/backend/schema/`, etc.

Pire, une des occurrences utilise la mauvaise casse : `custom_functions.dart:27` fait `FirebaseFirestore.instance.collection('parcelles')` (minuscule) alors que la collection canonique partout ailleurs (schéma, règles Firestore) est `Parcelles` (majuscule). Selon les règles Firestore hébergées (sensibles à la casse), cette fonction utilitaire pointe vers une collection différente et vide, ce qui est vraisemblablement un bug silencieux (la fonction — non identifiée plus précisément faute de temps — retournera systématiquement une référence vers un document inexistant).

**Correctif recommandé :** créer `lib/core/constants/firestore_collections.dart` avec des constantes (`Parcelles`, `Materiels`, etc.), remplacer tous les littéraux, corriger `custom_functions.dart:27` en `'Parcelles'`.

## 3. P2 — Amélioration

### P2-1. Résidus anglais dans l'UI, au-delà du composant déjà identifié

Le constat préliminaire #5 (chaînes anglaises dans `lib/components/imagepicker1_widget.dart:101,134,137`) est confirmé **mais ce composant est du code mort** : recherche exhaustive de `imagepicker1_widget.dart`/`imagepicker1_model.dart` dans les imports de `lib/` → aucun autre fichier ne l'importe. Il n'est donc atteignable par aucun utilisateur (à vérifier si un futur écran doit encore l'instancier, sinon le supprimer plutôt que le traduire).

En revanche, du texte anglais **bien vivant** existe dans `lib/auth/firebase_auth/firebase_auth_manager.dart` (utilisé par tous les écrans d'auth) :
- ligne 121, 137, 208 : `SnackBar(content: Text('Error: ${e.message!}'))`
- ligne 315 : `'Error: The email is already in use by a different account'`
- ligne 317 : `'Error: The supplied auth credential is incorrect, malformed or has expired'`

Ces messages sont visibles par l'utilisateur final lors d'erreurs de connexion/inscription — dans une app 100 % française pour un public peu à l'aise avec le numérique (CLAUDE.md §3.1), ce sont probablement les pires messages à laisser en anglais (moment d'échec/friction).

**Correctif recommandé :** traduire ces messages en français simple ; supprimer ou reconnecter `imagepicker1_widget.dart`.

### P2-2. Couverture de tests très faible et concentrée sur les couches ajoutées

**Fichiers :** `test/models/role_test.dart` (244 lignes), `test/services/rbac_service_test.dart` (255 lignes), `test/utils/validators_test.dart` (274 lignes), `test/services/offline_service_test.dart` (33 lignes), `test/widget_test.dart` (17 lignes, test par défaut Flutter non personnalisé).

Confirmation du constat préliminaire #7 : 5 fichiers de test pour ~47 400 lignes de `lib/`. Les tests existants couvrent bien les couches ajoutées récemment (rôles, RBAC, validators) — c'est cohérent et positif — mais rien ne couvre : les écrans (aucun test de widget significatif), le calcul financier (inexistant, cf. P1-1), le service Firestore/backend, ni les règles de sécurité (pas de test avec l'émulateur Firestore/`@firebase/rules-unit-testing`).

**Correctif recommandé :** au minimum, ajouter des tests d'émulateur pour `firestore.rules` avant tout correctif de P0-1 (pour non-régression), et des tests unitaires dès que le moteur financier (P1-1) sera écrit.

### P2-3. Palette de marque : tokens présents mais valeurs hex différentes de CLAUDE.md §3.2

**Fichier :** `lib/flutter_flow/flutter_flow_theme.dart:152-159` (thème clair), `:343-350` (thème sombre).

Confirmation du constat préliminaire #1 : le violet FlutterFlow a bien disparu, remplacé par une palette agricole verte/or. Mais en comparant précisément aux valeurs figées par CLAUDE.md §3.2 :

| Token CLAUDE.md | Valeur spec | Valeur code (clair) |
|---|---|---|
| `primary` Vert Demeter | `#265C2F` | `#1B6B3A` |
| `secondary` Brun terre | `#502E15` | `#E8A217` (= couleur « or maïs ») |
| `accent` Or maïs | `#C68A1F` | *(pas de rôle `accent` distinct dans le thème)* |
| tertiary | *(non défini dans la spec)* | `#7B5E3A` |

Le rôle sémantique ne correspond pas à la spec : le token `secondary` du thème porte la couleur or (qui devrait être `accent`), et le brun terre (censé être `secondary`, pour titres/en-têtes) n'apparaît nulle part dans les 3 tokens principaux. Ce n'est pas bloquant fonctionnellement mais c'est un écart direct par rapport à une section marquée comme design system de référence.

**Correctif recommandé :** aligner les 3 valeurs hex exactes de CLAUDE.md §3.2 et introduire un 4ᵉ token `accent` si le thème FlutterFlow à 3 couleurs (`primary`/`secondary`/`tertiary`) ne suffit pas à représenter primary/secondary/accent de la spec.

### P2-4. `firebase/functions/` : à vérifier vis-à-vis de la règle 🔒 n°8 (reset mot de passe)

**Fichiers :** `firebase/functions/index.js`, `firebase/functions/api_manager.js`.

CLAUDE.md règle 🔒 n°8 exige une Cloud Function admin pour le reset de mot de passe (impossible nativement avec emails synthétiques). Un dossier `firebase/functions/` existe bien, mais son contenu n'a pas été audité en détail dans cette passe (hors périmètre temps) — à vérifier explicitement qu'une fonction de reset password y est implémentée et sécurisée (auth admin, pas de fonction ouverte), sachant que côté client `MotdePasseOublieEmailWidget` existe (`nav.dart:320-325`, route publique légitime) mais son contenu exact n'a pas été relu ligne à ligne.

**Correctif recommandé :** passer `firebase/functions/*.js` en revue dédiée (sécurité + conformité à la règle 🔒 n°8) lors d'un prochain audit ciblé backend.

### P2-5. Dépendances git (non pub.dev) et versions figées manuellement

**Fichier :** `pubspec.yaml` (dépendances `dropdown_button2` et `flutter_google_places` via `git:` + `ref:` de commit).

Deux dépendances proviennent de forks GitHub épinglés sur un commit précis plutôt que du registre pub.dev officiel. Ce n'est pas anormal en soi pour un projet FlutterFlow, mais c'est un facteur de risque de supply chain et de maintenance (pas de mises à jour de sécurité automatiques, dépend de la disponibilité du dépôt tiers).

**Correctif recommandé :** vérifier s'il existe des alternatives maintenues sur pub.dev, sinon documenter explicitement pourquoi ce fork est nécessaire.
